# 团队协作：一次目标的共同完成

## 2026-11-12：管家唯一接单入口与团队执行闭环

本轮用户原话：“UIUX好好做做啊，很恶心啊现在。而且我们的管家也没有具备这个跟团队的一个链路打通啊。既然管家是我们的唯一入口反正这个做的很不合理啊我觉得。UI UX做的很丑，很恶心，很乱好吗”。来源为本对话对 v0.1.119 的后续纠正，日期按 Asia/Shanghai，精确消息 ID 未提供。这是对上一版产品结构与体验的否决，不能因为上一版构建发布成功而关闭。

当前起点 `04ed87cd804b6d6d8d6fc7449531f391f85ef887`。以下决定替代前轮把“发起协作”作为独立接单入口的 TC-01/02 设计；原运行、权限、问题、资料与未知回执规则继续保留。

### 当前已确认的断点

- 手动页面可准备一次性模型分工，管家 `teams_start` 却只能使用已有编组或制作计划。空编组用户无法从管家目标走到同一临时团队执行。
- 能力入口直接跳团队表单；协作页与工作详情没有准确的双向关联，用户必须离开管家巡视成员和找结果。
- 已有 `owner_work` 结果冻结、outbox、唤醒与回原会话链实际存在，本轮复用。待完成子协作却被前端统一描述为“结果已到，等待管家整理”，中途问题与授权没有成为原工作中可理解的状态。
- 最终回流还有一处原生断点：发起团队留下的操作回执使父工作通常停在 `needs_confirmation`，已有接手只接受 `completed/failed`，因此团队完成不等于管家会自动整理。当前修正以原生只读协作事实决定整理资格，保留主人对原工作的最终核对。

## 正式旅程与界面关系

1. 进入协作目录，首先看需处理和进行中的目标；已结束协作可回看。复用配置在编组标签中。
2. 发起协作：写目标，选快速分工或已存编组，必要时调整模型分工；确认实际目标、成员与轮次后启动。保存长期编组是另一种明确用途。
3. 进入协作概览：知道目标、当前进展、需要处理的问题以及现有成果。可打开原任务继续处理预算、授权、真实制作等上下文。
4. 查看分工：看工作项/成员职责、依赖、子任务状态和产出。控制动作与它作用的对象相邻，低频编组管理在详情中。
5. 沟通：默认收件人为负责汇总的成员；引用问题时锁定原问题与收件人。补充入队、明确修改方向、继续执行分别反馈。
6. 停止及返回：历史、消息和已共享资料可读；停止后仍可撤回资料。返回保留搜索、阅读位置、所选成员与未发送草稿。

### 2026-11-19：我回答一名成员的问题，由我决定是否马上继续（TC-14）

原团队上写着“保存原回答”，但桥在每次保存时都向协调器请求启动原分工；回到界面也看不出只是保存、是否已排队或为什么没继续。现在在这条原问题下分别选择“只保存回答”和“回答并继续原分工”。保存不发起执行；继续沿用当次剩余额度，不批文件操作、不增加权限。回执须匹配原运行、成员、分工、问题和回答后才清除对应草稿；排队不等于成员已经用过回答。

先保存也不会丢掉下一步：回原问题，若仍是主人已存的同一回答、原分工仍在等待，可选择“用这条回答继续原分工”。只提取原生保存的那份回答，不读输入框或预览，不另建回答、任务或收件人。中途失去回执，先核对原记录；只看见已保存不当作续接成功。

待主人手机核对：让一项已获准文件分工实际问一个问题，先只保存，确认没有新执行，再经过返回/重进，找到同一成员、原问题和保存的答复；点击用它继续，区分原生返回的排队、暂不能继续及消费。另一名成员不应收到这条回答，原有审批仍须单独处理。本次未触发实际执行或设备体验。

### 2026-11-19：一个人等回复，不阻塞另一人已获委托的下一阶段

同一件多阶段只读协作里，A 等主人，B 已完成第 1 阶段且下一阶段不依赖 A。过去协调器一看见 A 没结束就停下整队。参照 [Claude Code agent teams 的任务依赖](https://code.claude.com/docs/en/agent-teams)：是否能接下一项，应取决于那一项的前置工作，而不是全队是否空闲。现在沿原分工图继续已经安排、前置产出确已完成的阶段；不会新建分工、增加并发/预算，也不会替 A 回答。等待成员仍显示原问题/停点，其旧版文本不会混入 B 的新研究。没有可独立推进的分工时才回等待；任何阶段仍待主人时不发布全队最终结论。规定互相质疑的结构化辩论、手机工作与制作审阅不放宽关口。

待设备核对：在两阶段协作中让一个成员停在原问题，确认无依赖的同事进入下一阶段，有明确依赖的同事仍等待；只处理原问题后，再查看整队最终交付。这里只核对正式源码与静态证据，不把运行时序写成实测。

### 2026-11-19：给同一成员的文件补充只落到指定工作项（TC-16）

同一位成员可能先做清单 A、再做说明 B。过去管家明确给 B 发的要求，如果按工作项地址发送而没有另传子任务 ID，实际会退成成员通用消息。A 先启动便可能把 B 的要求带进自己的文件上下文并标成已消费。现在从原计划冻结工作项、负责人代次、工作项版本、成员和分工 ID；已有子任务时由原生存储复核后入原队列。尚未建子任务，只放进原团队已有邮箱，等这项工作照常开始才可取用。改派、改版或已结束都不改投；有实际接收才记消费。

“继续”附在这条补充上时，不再追到别的最新成员代次；明确区分补充已保存、未另派、已排队和准入后待核对。不新建任务或预算，单用工作项地址不新增自动唤醒。待手机核对：同一成员负责两个有先后顺序的文件项，A 处理时只给 B 一条不同要求；观察消息回执里的原工作项，确认 A 的文件和消费记录不含 B 的要求，B 正常开始后再核对它。未实际运行文件制作、模型或设备。

### 2026-11-19：从协作成果找到具体成员交回的原件（TC-11）

以前一旦出现共同汇总，成果面板就只剩汇总原消息；成员独立交回的真实研究任务只能逐层到进展、成员与阶段记录寻找。现在成果页保留共同结论，在「成员交付的原件」里按成员、阶段展示其实际产出节选。使用原生成员回执，不以指派文案、人数、完成状态或过时的研究记录代替成果；缺少原始凭据的老协作沿用原进展入口。这里的完成代表该成员交回了回答，不代表答案已核实。

按下一份原件时重读同一协作，再由既有原任务入口核对成员、阶段、研究任务、子执行代次及回答定位／摘要指纹。原件变更或不能核对就留在协作，绝不打开最新任务、另一个同名成员或另一阶段。返回保留原协作成果、展开位置与草稿；没有复制任务、重派成员、自动续接或新增授权。待手机验证：从多人已交付的协作分别打开两位成员的原工作，返回各自的成果条目，并在来源变化或前后台切换时确认不会串工作。

### 2026-11-19：研究员从主人所选公开站点找到下一页

把一个资料站点交给成员，无需同时知道文章的精确路径。原来的匿名读取只返回页面文字，真实链接地址在投影中遗失；另一个被列出的“搜索”实际不在成员工具权限里，而且会把查询交给不同的搜索供应商。现在从这一次已经获准、实际取得的 HTML 正文或导航中，最多保留八条有标题的同源 HTTPS 链接。复用[项目已有的 jsoup 相对地址解析](https://jsoup.org/cookbook/extracting-data/working-with-urls)，不猜路径，不访问链接，不发送查询。带账号、查询串、片段、下载标记或站外目标的不作为导航线索。

链接条目标明尚未读取。成员只有通过原来的匿名 GET、取得目标正文后才能引用那一页；目标没有正文、要求登录或依赖交互渲染，则留在原分工说明缺口，不要求成员调用未配备的交互浏览器。主人主动的全局搜索不受影响。待手机检验：只提供一个文档站点，用首页正文所含的同站章节链接取得第二页；确认第一份回执没有声称读过第二页。未调用真实模型、网络研究或更新任何账号权限。

### 2026-11-19：留给同一名成员下一阶段的补充（TC-12）

在两阶段研究中，管家可通过既有的 `teams_message` 明确指定某成员、第 2 阶段与 `queue`。原实现只在第 2 阶段已创建子任务时才保存阶段；收信又只看成员，导致第 1 阶段也能取走并记为已消费。现在排队回执保留目标阶段，不预建子任务。原收件成员在该阶段正常开始或恢复时才可领取；若已绑定原子任务，则新版本不接管它。同一发送编号不能改投其他阶段。轮次未指定的普通补充及队友来信，仍按既有队列规则处理。

[AionUi 2.1.40 官方更新](https://github.com/iOfficeAI/AionUi/blob/main/CHANGELOG.md)把负责人预热与指定成员接入分开，这里借鉴的是“选择接收者不等于启动执行”，不是照搬它的调度器。待设备核对：第 1 阶段进行时给同一人第 2 阶段排队一条明确要求，先看排队回执，再核对第 1 阶段没有消费、第 2 阶段使用该补充；其他分工不暂停、已完成结果不重跑。此次没有增加自动调度、权限或预算，也没有设备行为实测。

### 2026-11-19：区分“补充已送进原邮箱”和“另一次继续已入队”
管家给研究成员发送一条带“继续”的补充时，先有原消息持久化回执，然后才是原协调器能否继续。以前只要原成员本来就在途、同队还有执行或主人暂停，这个二阶段操作会在保存后抛错，管家不知道能否依赖第一步。现在在确知尚未进入调度前，返回同一消息编号、原成员/阶段、可投递或仅存档的状态，并分别注明本次没有另起执行及原因。实际已排入的才说已排入，不声称已经消费。发给未来阶段不会提前创建子任务，发给已结束原子任务会按 SQL 回执标为仅留历史。
续接只认保存这条消息时的目标、代次和原子任务；材料、预算、主人暂停及单队执行限制照旧。若原生继续已被受理，后续失败仍为待核对，不会谎称“未开始”。待手机核对：同一人仍在处理时补充明确要求，从原委托看到原消息已保存、没有第二次派发；回到成员相同阶段观察是否由真实答复消费。未触发实际执行。

### 管家收到独审结论，而不是把所有阻断都转成主人批准

原团队独审提交的意见和其最终答复不是同一字段。管家发起独审后可收到该次实际提交的原意见、工作版本和审阅者执行；稍后可从原审阅目录按原计划指纹重新读取。没有完整独审、明确要求修改、不能判断、项目基线变动和真正缺主人本版许可分别处理。审阅者意见不是主人指令；不代批、不自动发回作者、不重开已有整合者。

待手机手验：让本机双成员协作的独审实际指出一处需要修改，管家应能说出原意见，而不是请主人批准。独审明确无阻断但未获原许可时才提示核对；切换文件修订后按旧指纹重读应失败，不返回新稿。未在设备执行。

### 写回已发生时，不再显示“原项目尚未整合”

本机文件团队仍留在原主人的审阅流程，不因写入而变成业务成功。原唯一整合者返回后，只对精确原计划、原独审、成功写回回执与当时项目版本匹配的文件计数；团队记录说明这是上次核对。再次打开冻结文件则重读当前项目头，分别显示当前仍匹配的份数、尚未确定的操作或在运行的整合。回执不匹配不能当作从未写入，不能借此重放。

待手机手验：两份选定文本实际写回后回到原团队，核上次记录及当前两份匹配。随后在原项目单独改动其中一份，再次打开文件目录应为一份匹配，但不会改写上次观察、覆盖新内容或代主人验收。未在设备执行。

### 只继续这项文件分工，不借它恢复全队

管家批准一份含多个文件项的团队计划后，回答原问题或继续某个文件项，旧协调器仍会重扫整队。一个成员名下同时有 A、B 时，点名 B 可能把刚恢复的成员交给 A。本次保留原 Runner、单一协调队列、预算和文件授权，区分原计划派发与已经获准的单项续接。单项只匹配原成员代次、工作项版本、负责人代次和原 assignment；前置还没有真实冻结成果就不预留续接，也不替它启动前置。

原来正在正常工作的同事不被暂停；B 真实冻结后，仍在原运行及原成员代次中、确实依赖这份成果的已批准分工，可依原计划解锁。仅恢复 B 不解除另一个成员或该成员其余文件项的独立暂停，不把旧授权在重启后重建。已排队不等于已执行或交付。

待 Android 手验：同一成员有 A、B，B 等主人的原回答；从原问题只继续 B，核对首条实际分工及预算的原 assignment、A 的原文件回执不变；另一个已批准且依赖 B 的成员应在取得真实冻结回执后接续。另在暂停全队后只续 B，确认其他暂停项没有被带起；B 尚缺依赖时，不应出现一次新预留。此处仅为手验路径，未在手机运行。

### 在原分工核对后恢复，不把打开详情当成放行

当管家按原计划组织本机文件协作，成员的原任务明确记录为暂停、中断或失败时，展开同一工作项可“核对能否继续此分工”。先看原成员、工作项、准确文件路径和核对时实际剩余额度；返回不登记任何继续。明确确认后才沿原生 WorkPlanPage、TaskStore 及单项队列预留 1 次已有模型额度。原完整项目、远端命令、未回答问题、待处理审批、未知写入、尚在运行的子任务或过期草稿不能借此入口放行。主人可留在原分工打开已有任务核对。

待手机手验：A 的文件已交回，B 在仍有原授权的本机草稿分工遇到确定停点。展开 B，核对文件和现余额后返回，确认 A/B 没有新执行；再核对并明确继续 B，检查 B 的原 assignment 登记、A 的已交付文件未重跑。切后台、换成员或改工作项后，旧预览应失效；原流程未获准真机执行。

### 原成果页读真正的冻结文件差异

文件协作进入待审阅，或已有实际冻结文件，主人在该队“成果”里可直接读取打开时的原项目与原成员文件比较；普通任务详情不再是唯一去向。文件行来源是本次原生计划中的 artifact、assignment 和成员，不按同名文件或最新任务匹配。不同成员交的文件能逐份辨认；项目基线已变、之前已整合并仍匹配回执、未交齐、二进制和删除记录分开表示。

差异按需逐段读取同一份有界、只读快照。空文本差异不是缺文件；被原生比较截短不标为完整，二进制/删除不伪造文本。返回留在这次团队成果，换团队、切后台或原身份变化需重读。仅打开和翻阅不会批准、启动、整合或表示业务成功；正式独审与主人的批准是另外的动作。待手机手验：两个成员各交一个文件，从原成果页分别打开；查看跨页的文本差异和无文本的文件，退出再核原项目未改。未在设备执行。


### 核对这版文件，并单独批准写回许可

当管家等待本机已选文本的首次写回许可，主人可在同一份文件目录看完各页，单独核对原项目和每个新增/修改路径后，再明确勾选并批准。原生登记原版本的一份许可；这使管家之后可按原父任务授权请求唯一整合者，不是已经写入、启动模型或业务验证成功。返回文件不批准；切后台或换窗口关闭尚未提交的审阅。结果不确定时重新打开原目录查原登记，不重投。

只接受已取得同一版完整、无阻断独审的原计划及已加载的完整普通文本差异。项目基线改变、未交齐、二进制、删除、截短、恢复、完整项目或远端执行不能在此批准。批准前重新读取冻结原文、项目版本和独审身份；不扩大原文件/命令范围。
待手机手验：两位成员各交本机文本，管家独审完成。在一个长差异还没读到末页时不应能核对许可。全部加载后先看路径并返回，核原项目和批准记录不变；再次核对并明确批准，重开可见原登记，但本动作没有写入项目。改动原项目基线或切后台后不应复用旧预览。未在设备执行。

### 从发起工作的原对话找回本版文件审阅

两位作者都交付后，成员待办可以是零，但文件独审可能刚刚完成。原工作行另按真实独审回执提示“核对独审返回的 N 份文件”，不把整队的“等待审阅”或同名成员视作许可。列表只带原父工作、项目、独审执行和版本标识，不拷贝路径、差异或独审正文。点击先核对当前冻结版本和项目基线；符合时打开同一团队已有文件目录。关闭返回原对话/草稿，不发补充消息。聊天入口不批准；写回许可只在原成果内按已有单独确认办理。若版本已批准、撤销或切换，原来的入口不应把人送到另一版。

待手机手验：原对话保留一半草稿，等待本机两位作者和独审真实返回。成员待办为零时从原工作点文件，核对项目、贡献成员及长文本；关闭应回原草稿。另使同队完成新独审、在别处批准，或改原项目基线后再点旧入口，应留在或返回原对话，不展示新版本。未在设备执行。


### TC25 · 管家针对已写回原件提出修订，主人按本次范围接回原作者

正常旅程：原本机所选文件团队有两项独立分工，另有一项依赖第一项。唯一整合者写回实际文件之后，管家把具体修改意见留给第一项。原成果页从这一次父操作读取原提案；读提案或核对修订不是同意。确认页展示完整原文、实际受影响项与每位原作者、逐条路径与版本、不重跑的项数，以及新旧团队模型/工具总额度和已用或预留量。只有主人单独确认才通过原 WorkPlanPage 审阅与 TaskStore 审批；新隔离草稿仍需重新独审/许可才可写回。这个入口不增加父授权，不开放完整项目、远端或命令。独审退回且未写回的版本只能保留原意见，没有用先写后改绕过独审。

**父工作怎样辨认后续回执。** 主人同意的是新隔离草稿，不是本版写回。父工作中断后重读状态，不需要猜原提案：已登记的原整合者标注属于修订前还是这次新许可。查询修订后的文件时，原生将原提案与 TaskStore 的同一修订编号、受影响工作项的历史回执及旧整合者核对。新作者还未交齐、独审未完成、独审退回、独审通过但仍缺本版许可、已有本版许可是不同结果。原文件的 V1 成功回执不冒充 V2 写回；V2 若确有独立批准，返回所问版本的许可和那个唯一整合任务的实际状态，不用后续比较冒充所问原件。读取和重复请求均不会启动/重试旧整合者；此处没有新增第二次写回的前台许可或执行入口。

待机主手验（未触发实际执行）：从原团队成果打开父提案，取消一次，分工、额度和原件应不动；重开核对第一项和依赖项的原作者、文件和额度，再仅在确实愿意开工时确认，第三个独立成果应原样保留，已提交的同条提案不得再执行。核对后若离开私人前台或项目实际文件发生变化，旧确认须失效。给未写回的退回稿提出意见，只可读，不应出现开始修订按钮。

### TC26 · 从发起工作的原对话找回那一条修订提案

父工作行将同一轮、已写回版本的管家修订提案与成员问句、首次文件许可分开计数。点击才读原父任务/执行/代次/私人对话所指团队的小目录；同作者、同题分工用明确标注的原提案节选辨认（最多 72 个 Unicode 码点）。选择时核对原操作、分工、assignment 和该版实际整合回执及当前项目文件头；团队结果也重新核对，只展开这一条。这里只是前往原件，原有范围核对和主人明确确认必须另外操作。本次不创建调度、许可或任何项目写入。

待机主手验（未在设备执行）：保留原对话未发草稿，同一作者的两个同名分工均有提案时从原工作点选第二条，核对实际原文/作者；返回原对话应保留草稿，不应发消息。另在确认前切后台，或改原项目文件/已在其他窗口处理该提案，旧入口须拒绝或明确已不再等待，不自动打开另一个提案。被退回未写回的独审不能出现这个审批入口。
