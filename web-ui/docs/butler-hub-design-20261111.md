# PocketWorld 私人管家中枢：功能与 UI/UX 设计提案

状态：设计候选，尚未实施、未取得用户对本方案的视觉认可。核查基线：v0.1.103，源码 875dfee8，文档入口 220560c7。编写日期：2026-11-11。完整实现事实与此前修正保留在 [DESIGN.md](../DESIGN.md) 的 PW-H1–H4；本文件承担本轮深度设计，不重复维护发布状态。

## 1. 本轮目标与原话

用户原话：“还差啥缺口？如果让你设计一个我们这个的 ai 应用有个核心中枢的权威入口管家你应该怎么设计功能？以及 uiux 请你深度设计”。来源：本聊天最新用户消息；记录时间 2026-11-11，精确消息 ID 与发送时间不可取得。

承接已保存的纠正：给普通对话加上管家标签，不能证明工具、能力和全系统链路已形成中枢。本轮要求记为 PW-H5：在当前源码和已批准组件基础上，给出整体功能关系、关键旅程、UI/UX、状态与恢复、可执行的落地顺序。设计建议、用户授权实施、用户认可效果分别记录。

本轮范围：深度产品设计、实际源审、成熟机制比较、对话内交互方案和可持续的设计记录。实现不在本轮设计完成的声明范围内；不更改生产执行协议，不运行任何测试或采图，不在本机构建 APK。交互方案使用明确标注的示例内容，不连接或改动真实任务。

## 2. 核心选择：一位持续负责的管家，一份可追踪的委托

管家承担六项责任：理解用户目标；判断当前能做什么；安排工作；接住进展、阻塞和结果；核对结果与目标的差距；将有用的成果和获准的长期理解保留下来。

“权威”来自明确责任和同一事实源：它能够回答每件事为何开始、现在到哪里、谁在执行、缺少什么、出了什么结果、下一步由谁决定。用户的指令与控制仍是最高产品权威，模型的一句“完成了”不直接修改执行事实。

推荐 COMBINE 路线：统一自然语言接待 + 可直接操作的工作对象 + 项目现场 + 成果版本。保留现有 TaskStore / AgentRunner / RunControl 作为唯一运行事实源。管家是产品中的主协作对象，不是要求将所有工作塞进一条无限增长的聊天，也不是引入第二个执行器。

### 2.1 已比较的路线

| 路线 | 价值 | 现实问题 | 决定 |
| --- | --- | --- | --- |
| 超级聊天：能力都挂在一个输入框上 | 接待门槛低 | 长工作、成果、批准和状态会淹没在消息里；很难确认一句补充送给了谁 | 保留自然语言入口，补持久工作对象 |
| 任务仪表盘：先建项目、任务、执行器再运行 | 结构明确 | 用户被迫替系统做编排，首次使用成本高 | 管理视图作为辅助，不作为交办前提 |
| 多代理工作室：前台呈现所有成员和线路 | 专家可精细调整 | 普通用户承担选择和巡视各 Agent 的成本 | 团队详情渐进披露，仅在用户想控制分工时展开 |
| 负责到底的管家：目标进入，工作推进，成果返回 | 兼顾低门槛、可见控制与长期连续性 | 必须补齐真实事件、来源和控制回执 | 推荐产品方向 |

## 3. 当前基础与剩余缺口

下面的“已有”来自源码，不等同当前 Android 完整体验已通过。

| 领域 | 已有基础 | 关键缺口及用户影响 |
| --- | --- | --- |
| 接待与委派 | 普通私人管家、独立 owner_work、原请求与工作身份 | 接单主要记录 goal/title/budget，缺少统一的产物、约束、验收和完成责任；说“交给我”后没有完整承诺 |
| 能力理解 | DeviceCapabilityRegistry 已区分 implemented、installed、authorized、ready、busy、reason；tools_search 可找本次准入工具 | 模型没有覆盖全系统且遵守原策略的准备状态目录；可能不知道需要选择哪个项目、设备或账号 |
| 手机与项目 | 原生手机准备、审阅、启动；ProjectOwnerWorkflows 的项目/副本/环境绑定；真实任务和控制 | 管家缺有来源的正式提案到原生入口的交接；用户仍需自己找入口和重复交代 |
| 工作总览 | 原生最近委派 UI；持久跨话题状态目录；原会话定位 | 全局目录只是身份/状态元数据；跨话题正文与操作不能仅靠列表可见放行 |
| 结果回流 | 冻结成果、outbox、原会话投递、结果引用与接收证明 | 投递后没有真正唤醒管家处理；必须等用户再次说话，管家才可能读到 |
| 长期执行 | 独立工作、预算、原生暂停/停止；远端与团队执行 | 父工作结束后，远端/团队晚到结果不能自动接回父级；接纳回执可能被误当完成 |
| 决定与恢复 | 原任务原生问题、批准、运行控制、精确 review handle | 首页的“待处理”主要跳任务详情；缺统一解释与生效回执，继续可能被误解为批准 |
| 成果与版本 | WorkspaceArtifacts 不可变对象、task/run 来源、sourceRevision/sourceVersion；项目包 versionSequence | 管家未按验收逐项判断与解释；保存产物不代表内容已核实，project_bundle 保留 businessVerified=false |
| 记忆与来源 | 主人资料、获准记忆、来源同步、纠正/忘记 | 跨话题派生正文的历史、后续任务、学习与正式记忆还缺完整上游来源传播 |
| 资源统筹 | ExecutionResources 主屏独占、后台 token；PhoneAppResources 应用副本占用与等待环 | 管家与 UI 还需把这些事实转成“谁在占用、会等什么、能否换路线”的产品反馈 |

这些基础足以支撑增量改造。缺口集中在关系、接续和可靠表达，不能通过增加一批工具按钮来关闭。

## 4. 产品对象：用户交代的是一件事

| 对象 | 对用户的含义 | 关系与规则 | 实现映射 |
| --- | --- | --- | --- |
| 管家 | 持续负责的同一协作对象 | 跨话题掌握获准的工作，统一接待与汇报 | 现有 OWNER_BUTLER 与私人宿主 |
| 话题 | 一段具体沟通现场 | 可纯讨论；可产生多件工作；不用每次更换 Agent | 现有 conversation |
| 工作/委托 | 一件需要落实的目标 | 稳定身份；保留原话、目标、范围、约束、交付物、当前责任与下一步 | 现有 owner_work 为主；原生专项任务通过原生签发关联加入 |
| 执行 | 工作的一次具体尝试 | 可能有多个 run、子任务或团队成员；不把每次重试当新委托 | TaskStore / runId / epoch / RunControl |
| 项目 | 一段持续工作的资料与成果现场 | 可容纳多个话题和工作；不是只能放代码的文件夹；不要求所有临时工作都进项目 | 现有项目、资料和 developmentContext，按真实类型渐进扩展 |
| 成果 | 可打开、引用、修改的交付物 | 有稳定身份和不可变版本；继续修改时显式引用版本 | WorkspaceArtifacts、文件、项目产物 |
| 决定 | 只有用户或明确授权规则能作出的判断 | 依附准确工作和原生操作；不会因切页面或模型说“继续”而消失 | 原问题/批准/准备/核对对象的统一投影 |
| 长期记忆 | 可复用且有来源的偏好与知识 | 有适用范围和失效关系；工作即时状态仍读事实源 | 现有主人资料与记忆系统 |

命名上普通界面统一用“工作”。“任务/运行/Agent”进入细节或专家视图；不能在同一层用不同词指代同一对象。项目、成果是可直接访问的对象，用户不必每次通过聊天拿到它们。

### 4.1 最小工作合同

每件真正接手的工作，至少保存以下内容：

- 用户原请求与后续修改的真实来源。
- 要达到的结果，以及可观察的完成条件；简单问题直接回答，不强行创建工作。
- 交付物类型与归属，例如可编辑报告、截图整理清单、某项目的代码变更。
- 本次范围和明确约束，例如只整理不删除、只改欢迎页、先给草稿。
- 当前资源选择、可用能力、准备缺口、并行依赖。
- 执行额度和结果接手额度；是否允许主动继续、何时停止。
- 当前执行身份、待决定事项、已保存成果、管家处理回执与下一动作。

上述结构大部分由管家从请求中整理。面向用户展示两三行接单说明，关键冲突才展开问；不用先填一个项目管理表单。不同目标或范围变化应留下合同修订，正在运行的任务读取了哪一版要能追踪。

## 5. 六条关键用户旅程

### 5.1 第一次交办：从目标直接到可开始的工作

用户：“把这些 AI 应用资料整理成一份中文周报，重点写对我们有用的点，放进研究项目。”

管家先识别所需资料、项目和产物。已知唯一项目并有权限时自行绑定；有两个同名项目或会影响覆盖范围时，显示具体候选。接单说明：“我会整理成可编辑周报，保留来源，并放进研究项目。先归纳变化，再核对来源，最后整理建议。”

原生系统确认工作建立以后，出现同一工作条目和“已接手”。模型仅表达意愿时不能提前显示正在执行。简单、可逆、已授权步骤直接进行；需要新的真实资源选择时在原位补齐。

### 5.2 执行中继续聊：每条补充都有明确落点

用户：“别超过两页，社区吐槽也留一点。”

如果当前明确选中周报工作，直接提交成该工作的补充。输入框上方轻量显示“补充给：AI 应用周报”。收到原生回执后显示“已补充到周报工作；整理阶段会采用”。如果写作已结束，应说明“已生成第一版；我会据此修改第二版”。

用户：“顺便帮我改一下项目欢迎页。”这会形成另一件工作，管家无需中断周报。工作状态与前台输入状态分离。两件工作都可能接收“先停一下”时，才在输入旁让用户选目标；不能默默停错。

聊天草稿、给工作的补充、待批准的答复分别保存。切换工作不把未发送文本自动重定向，也不通过导航触发发送。

### 5.3 需要设备或项目：准备完成后回到原委托

管家先准备有来源的执行提案，指出这一步为什么需要资源。项目提案含实际项目、工作副本、环境与预期修改范围；手机提案含准确设备/应用与操作目标。

原生准备页只解决当前缺口。选完副本、完成登录或打开相应能力后，返回同一工作，保留目标与草稿并重新核对资源状态。配置成功、授权成功、实际可运行是三个事实；不能保存设置后直接声称任务已执行。

正式启动复用现有原生审阅与准入。管家不能自己写 developmentContext 或挂载无范围的手机端口来省略用户真实选择。

### 5.4 用户离开：执行可继续，结果有人接

前台对话结束不取消已授权的独立工作。需要本机在线的步骤，明确显示“依赖这台设备在线”；设备无法继续时记录等待或中断，不能承诺离线仍在做。

结果到达后，原 outbox 保存成果和原生接手事件。原会话空闲且原授权、来源和预留额度仍有效时，由同一 TaskStore/Runner 启动有限的结果处理。原会话忙则合并等待，用户回来仍可看到原始成果。取消、过期、来源撤销时不自动执行。

管家核对本次目标，形成“已完成什么、产物在哪里、还有什么没达到、下一步是什么”。需要返工且仍在范围/额度内可继续，否则提出具体决定。不给一份原始子 Agent 文本加上“已完成”就交差。

### 5.5 从成果继续：版本和修改对象明确

用户打开周报第一版，选中一段或输入“把建议再压缩一点”。输入会带上原成果与版本引用。新执行产生第二版，保留第一版和变更摘要；用户可直接比较、选择使用、继续改。

若文件已被用户编辑，读取当前 head 与原版本差异，明确继续基于哪一版；不能用旧模型记忆覆盖新文件。结果列表默认当前有效版本，历史版本在对象内查看，避免目录堆满同名文件。

### 5.6 隔天回来：管家先回答哪里需要关注

应用恢复先同步事实源。首页优先显示有意义的变化：已可查看的成果、用户必须决定的事项、因真实问题停住的工作。普通运行过程保持安静。

管家可基于获准内容给出简短汇总：“周报第一版已整理；欢迎页工作等你选择副本；截图整理仍在等手机上线。”点击任一句进入准确对象。没有读取完成的全量数据时显示“最近工作”，不声称“全部完成”。

## 6. 能力与编排：按目标组织，按真实条件执行

### 6.1 用户看的是能做什么

能力页按目的组织：查资料、处理文件、修改项目、操作设备、连接外部服务、安排持续工作。工具名、MCP、模型和执行器进入展开详情。工具数量不是能力质量指标。

能力状态建议统一为：可直接使用、需要选择资源、需要准备、正在占用、暂不可用。展开后分开显示支持、安装、授权、登录、设备可达与资源占用；不把“已安装”做成绿色“可用”。

模型取得的是本次策略允许的能力投影。工具目录、只读状态、正文读取、动作授权分开；沿既有 beforeTool、scope 与 deny/ask/review，不能以自动首页 briefing 绕过原工具拒绝策略。

### 6.2 编排选择与并行

管家按工作需要选择执行途径：本地资料/工具、项目执行、手机能力、远端工作或团队。稳定重复过程可以采用已保存的工作方式；有独立研究分支才并行。

复用现有 ExecutionResources 与 PhoneAppResources，尊重主屏独占、浏览器/手机互斥、后台 token 和应用副本占用。发生冲突时显示事实：“另一件工作正在使用手机，完成后继续”，并提供支持的换路线、调整优先级或停止动作；不在 UI 伪造独立调度。

执行器故障只影响相关分支。管家说明哪些结果仍有效、哪些需补做。团队页保留成员进展与事件，但主界面只展示影响目标的阶段与阻塞。

### 6.3 主动职责的边界

第一层主动性是完成已交办工作：等待资源、接回结果、范围内修正和汇报。第二层是用户明确设置的定时/条件职责，例如每周整理资料。第三层是机会建议，默认只提出，不自动扩成新的执行承诺。

持续职责只有实际持久触发器、预算、环境和通知渠道建立后才能显示“已安排”。展示下次触发、上次执行、错过/失败原因和暂停。事件需去重，结果未知先核对，不盲目重放对外动作。长期主动职责放在完整交办闭环之后实现。

## 7. 状态与控制：表达已发生的事实

### 7.1 四个维度不能压成一个 completed

| 维度 | 典型状态 | 面向用户的表达 |
| --- | --- | --- |
| 执行 | 等待/准备/执行/等用户/暂停/停止中/终止/失败/结果未知 | 正在核对来源；等待手机上线；正在停止 |
| 成果 | 无产物/草稿/已保存/新版本/部分可用/来源失效 | 第一版已保存；还有两处资料未核对 |
| 管家接手 | 待接手/正在核对/已汇报/需续作/无法继续 | 执行结果已到，管家尚未整理 |
| 用户决定 | 无需决定/待决定/提交中/已生效/已过期/结果待核对 | 选择工作副本；修改已送达；状态变化，请重新查看 |

实现可保留更多内部状态，UI 显示当前最重要的一个状态和原因，再按需展开。没有可信进度分母时显示当前阶段和最近事件，不能造“完成 80%”。

### 7.2 统一决定入口

“待你处理”是一处集中入口，里面是不同原生决定对象：补资料、选方案、允许具体动作、解决准备缺口、核对未知结果。每项回答：为什么要你决定；影响哪件事；具体选项及后果；系统推荐与理由（确有依据时）；暂缓会怎样。

普通输入补充可行内处理。涉及文件差异、设备范围、账户或对外内容时进入完整审阅页面。批准前展示已经准备好的具体内容；批准绑定准确资源、版本和操作。重复点击不会重复执行；提交后保留行并展示状态，只有原生回执确认才移入已处理。

“继续工作”不会替代“回答原问题”或“批准某操作”。失效的决定不能沿用旧按钮；刷新后说明变化。未知结果提供“核对结果”，不能放一个看似安全的“重试”暗中重复发送。

### 7.3 控制动作的作用范围

- 停止本轮回复：只停止前台生成，保留已创建独立工作。
- 暂停这件工作：停在支持的安全边界，保留成果和可恢复信息。
- 停止这件工作：沿原关系控制全部相关分支；列明正在停止或无法确认的分支。
- 暂停主动安排：停止新的主动职责触发，已运行工作另行明确处理。
- 继续：从最新合法状态重新准入；不默认重放未知外部操作。

控制的“已提交”和“已生效”分开。跨话题操作在未来完整来源合同建立后由管家完成，用户不应永远被迫去原聊天重复说话；实现前保持当前原话题边界，不能把临时限制写成最终产品目标。

## 8. 记忆：理解用户，也尊重信息的有效范围

三类资料分开：稳定偏好（例如报告格式）、项目知识（例如产品定位）、实时工作事实（例如某文件是第二版）。前两者按范围检索，后一类直接读取权威状态。一次临时改向不自动升级成全局习惯。

“我与管家”页提供偏好、正在承担的长期职责、已记住的内容、允许的自主范围、设备与连接概览。记忆可查看原来源、修改适用范围、更正或忘记；它们服务管家，不是另一套需要用户维护的知识管理负担。

跨话题引用先定位获准对象，再读取所需正文并附原生来源证明；不要把全部对话无限注入每轮请求。界面可显示“参考了：项目约定、周报第一版”，按需展开具体依据。

撤回一份来源后，下一次请求、历史读取、派生总结与正式记忆均应检查依赖。用户编辑/删除结果消息和上游工作撤销是不同生命周期。仍保留的产物注明来源变化，需要时重新核实；不能靠记忆继续传播已撤回的结论。

## 9. UI 信息架构

### 9.1 导航层级

默认入口始终为管家。辅助导航按频率与对象分组：

- 管家：交代目标、看新变化、处理必要决定。
- 我的工作：全部/进行中/待处理/已结束，查找和管理持续委托。
- 项目：持续资料、目标、工作、成果和项目约定。
- 成果：跨工作找回交付物；不和原文件系统混为一谈。
- 话题记录：沟通记录，位于辅助区域和搜索结果内，不和管家争夺主入口。
- 我与管家：长期偏好、职责、自主范围。
- 能力与设置：模型、设备、连接、工作方式与运行条件。

不增加一个与管家等权的 Agent 广场，不把技能/工具/模型/团队全部排在首屏。全局查找可以按工作、话题、项目、成果和来源筛选，结果展示归属和时间。

### 9.2 首页的三种布局状态

**首次或空闲态**：简洁标题、两层输入面、少量贴近已就绪能力的例子。模型未准备时只突出连接模型，其余能力到使用时准备。没有工作不造统计，不为了填空展示整套功能。

**回访态**：一句真实变化摘要；可查看的关键成果；当前待决定；进行中工作。输入仍容易抵达。只突出本次最有价值的一项成果，其余作为低权重对象行，避免全屏等权卡片。

**有工作进行态**：输入保持可用，轻量显示其归属；进行中工作显示目标和当前阶段。后台变化不抢焦点、不把输入框顶走，不让未读事件无限推高页面。

首页只给有界摘要，展开“查看全部工作”到完整目录。数字必须由真实全量查询提供；有界投影只能说“最近”。

### 9.3 话题页：沟通主线与工作关系同在

正文聚焦用户目标、管家判断、必要问题和结果。执行进程默认折成一条阶段摘要，可展开查看工具和子任务。工作以可点击的语义对象行嵌入对话，不让每个工具调用都成为大卡片。

输入框上方显示当前目标：继续此话题、补充给某工作、引用某成果第几版。用户通过上下文动作改变目标；新话题动作明确。模型/权限/附件沿已批准控件渐进披露。

宽屏有与当前工作相关的详情区，默认显示目标/成果/过程；没有明确工作时不为了凑三栏强开。手机点工作行进入完整工作页，返回原消息位置和草稿。

### 9.4 工作页：第一屏回答四个问题

顶部显示目标、状态原因和归属；主要内容依次是：当前做到哪、有什么成果、需要我做什么、接下来会怎样。

目标/成果/过程为同一对象的查看角度。目标页保留完成条件、资料范围与用户补充；成果页先预览可用结果和版本；过程页按阶段组织事件，展开才见成员、工具与运行细节。暂停/停止保留明确作用范围，低频控制放更多菜单。

状态发生变化时优先在原位置更新。用户正在阅读过程，不自动切到成果；用轻提示指出新版本。只有用户选择才切面板。

### 9.5 决定页：做得了决定，回得去原事

简单选择沿已批准 DecisionInbox 行内展开。较复杂的文件差异、设备准备和权限审阅使用已有 ReviewCenter/PermissionReview 页面。上方保留工作名称和原因，底部主动作写具体结果，如“使用此工作副本”，不统一写“确定”。

移动端完整页面承担需要阅读和比较的审阅。Popover 处理短菜单，Drawer 只用于已批准的短暂选择或导航；不能把所有详情、项目、长审批都塞进底部抽屉。返回恢复来源页面的阅读位置。

### 9.6 项目与成果

项目页按“当前目标与进展—待处理—近期成果—资料”组织。工作、资料、成果和约定是局部标签，文件树只是资料的一种查看方式。项目上方可直接向同一管家交代事情，自动带上真实项目引用。

成果详情把内容放在主区；标题旁是版本、所属工作和更新时间；来源、核对状态、修改记录按需展开。文档、图片、网页、代码差异、文件清单使用对应既有预览，不统一降成附件气泡。主要动作是打开/继续修改/使用，下载与更多操作次要。

### 9.7 手机与宽屏

| 情境 | 手机 | 宽屏 |
| --- | --- | --- |
| 管家入口 | 单列，20px页边；输入和重要变化优先 | 主内容约680–760px，辅助导航常驻 |

## 10. 视觉与交互规范

继承当前 product.css / presentation-theme.css 的中性色和低饱和蓝灰强调色：浅色 accent #526B8A、soft #EAF0F7；深色 accent #A9BCD6、soft #252D3A。颜色只表达选择、重点操作和必要警示；完成主要用文字与图标，避免把所有东西染绿。页面与表面通过微妙色阶、留白和必要投影区分，普通信息行不套卡。

动效沿现有 Motion 与组件参数：Tab选中指示在原位移动，列表按稳定工作身份更新，按压/展开局部响应。禁止统一给每页加Y方向入场导致跳动；禁止消息更新整页重排；中途切页/返回/打断应停在正确对象状态。reduce motion 关闭空间位移，保持状态反馈。未知加载显示最近更新时间，失联不永远转圈。

## 12. 与现有系统衔接的必要合同

### 12.1 接单与派发

沿当前 owner_work admission 增补原生工作合同与关联，初始用户引用必须来自真实消息。手机与项目以正式提案调用现有准备/审阅/启动；成功后把原生签发的 task/run 关联回原委托。标题或模型生成的JSON不构成绑定证明。

### 12.2 结果接手

派单时一并确定原接手者、目的地、源关系和真实预留处理额度。子工作结果沿既有冻结结果/outbox进入待接手状态。幂等键使用准确工作/结果版本/接手用途；领取、准备、物化和正式回复保存沿原事务边界，重复事件不重复执行。

H-A新增的管家汇报必须保留所消费结果的准确版本及上游来源依赖，贯穿本次模型请求、正式回复保存和同话题后续读取；原来源失效后不得继续把派生正文作为有效上下文。当前conversationRequest未完整保留这类证明，因此不能只在领取outbox时核查。历史显式读取及任何记忆学习若可能消费这段新汇报，也必须保留依赖或明确拒绝该条未经支持的消费，不能绕开失效规则。H-C再扩展跨话题和更广关系，不能将H-A自身新增内容的来源闭环后置。

会话忙时等待；取消、过期、来源撤回时终止；结果未知只核对确定事实，不自动重放。已发送模型请求但无法确定结果的情形单独保留。不能伪造USER消息，不事后补满预算，不另建一个调度器。

### 12.3 远端/团队关联

保留“已接纳”“执行终态”“父级已处理”三个事实。晚到结果落原父工作关系，触发同一种有界接手。部分完成时可先提供有效成果，但不能把还在运行的必要分支静默遗忘。停止动作沿同一关联传播并逐项确认。

### 12.4 来源与跨话题

从真实保存消息/运行事实签发证明，读取时复核范围、版本、删除/退休状态，并将依赖传播到当前模型请求、后续消息、历史读取和正式记忆。不能信任导入或模型自报的task/run字段。继续复用当前锁序，不在MemoryBook持锁的resolveMetadata里反向取得TaskStore锁。

### 12.5 UI事实投影

首页、工作页、话题、项目、通知是同一对象的投影。事件负责及时刷新；重进应用、重连和关键控制后回读权威快照，旧快照不能覆盖新事件。视图可有不同密度，但状态含义、目标身份和动作结果相同。
