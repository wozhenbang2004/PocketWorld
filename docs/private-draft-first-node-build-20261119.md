# 从所选私人改稿验证第一次本机 Node 构建

**实际路径。** 原话 → 这份已固定差异/已保留修订 → 建立并打开独立工程 →「验证这份改稿的 Node 构建」→ 核对本机运行位置、默认模型配置、源码版本和 package.json 声明的 build / 可选前后脚本 → 开始这项交办。此时只是一个新的私人任务，没有给命令授权。原有未发目标或手写约定不被覆盖。

- 只有曾由这一个稿本建立的本机普通副本才有入口。原 task、根稿、修订、SHA 生成的原生身份绑定新的 project / checkout；取其原稿库行及实际私有登记，并将副本**整树**与建立时比对。打开真正存在的副本后，母工程后来变化不影响它；反之不能把后来编辑过的副本当原稿做第一次构建。
- 本次只支持有非空 build 脚本且手机实际识别其 npm / pnpm 的 Node 工程。语法检查不是构建；缺少工具、需要依赖、文件变化均不静默改用原工程、下载、切到 Termux 或云端。项目脚本可运行自己的逻辑、写副本及联网；不能将脚本描述成只读或安全沙箱。
- 准备交办时、启动时和实际执行处重核工程/整树/本机运行身份及同一个原生 build plan。独立工具面只允许这个构建、同一任务的状态与日志、原成功 build 所选输出的核对和保留。命令和收集文件分别走既有 SQLite 原操作、机主批准、派发与回执流程，没有借旧工程、团队修改、开发服务或宽松自动权限。没有自动装包、运行服务、打开文件或发布。
- 手机端核对到原命令退出后，退出 0 只代表命令成功，不证明有产物。可读原 build 观察到的 build/dist 清单；实际保留文件需再次明确批准，并校验原 job、同版路径/容量/SHA 和落入 B4 的真实字节。可从同任务较早轮的成功构建选择输出。待批准时会分开显示源构建的 run/epoch/op 和此轮收件提案；批准后若新开一轮，以真实保存操作为准，而非把提案当保存或把旧文件说成这次生成。失败时从原执行读退出与日志、决定下一步；未知只查原操作。
- 续步只接受同 run/epoch 在原 TaskStore 登记的 planRef，不接受模型自带完整方案。只有原提案已由主人批准、已查证未派发、有效原能力与所选文件仍相同，才能按本轮重挂的引用继续；新执行和原提案不是同一操作。最后发送给模型的工具、恢复与新回复的整批调用还有限定；通用提问、计划、技能及其他工具不能混入。
- 在原话的那一稿重开可看到同一构建交办，并直接打开。来源是原 Assistant 邮箱请求 → 实际任务上下文，不按当前工程名或最近运行猜。原话展示当前轮最后一次构建/收件的原生结果；模型单说“成功”、上一轮的通过、待批准或不完整的回执均不作本轮完成证明。工程后来修改不会隐藏已建立的历史工作；找不到构建任务也不挡已有副本。

**开发环境观察，不是真机。** 无外部依赖的中性 Node 工程在 B52 单文件改稿派生出的 Linux 工作目录里手工执行一次 npm run build。原件 SHA 为 124d3c6b…；29 字节 dist/receipt.txt 和选中的稿 SHA 均为 44f4731d…，原工程没有 dist。真实 Java 预检只读源码和所选工具事实，未执行项目。没有调用在线模型、Android 安装包、设备服务或用户项目；Linux 结果不替代 Android 原任务及批准联验，不证明 APK 编译。
